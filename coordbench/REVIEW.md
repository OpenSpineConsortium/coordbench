# coordbench review: confirmed findings to fix next

A review in five lenses (MCP conformance with the real claude client,
fidelity to CooperBench, the runner against real docker, concurrency and
robustness, and a newcomer writing a new arm from the README) ran on
2026-10-09 with two skeptics per finding. These 28 survived both skeptics
and are not yet fixed. Of the 23 refuted findings none needs action. The
usability lens's findings could not be verified (the plan's usage ran out)
and are not listed; re-run that lens alone when there is usage to spare.
Delete this file in the pull request that fixes the last of them.

Start with the blocking ones: the 60-second MCP tool timeout against
wait_for_message, the server instructions that reach the system prompt
(a difference from CooperBench's prompt), the team task-list mirror that
follows symlinks on the host, and report.py reading CooperBench's solo
runs (singular "agent").

- [mcp, blocking] experiment/coordbench/arms/team/.mcp.json: With the shipped HTTP config, Claude Code aborts any MCP tool call that runs longer than 60 s. The team arm's `request` tool advertises waits of up to 300 s (arms/team/arm.py:88 LONGEST_WAIT_SECONDS, schema maximum 300). When the client gives up, the hub's thread keeps waiting and still takes the response, so the response is lost. The source is the client's own code (Claude Code 2.1.295, `wrapFetchWithTimeout`). Every non-GET request to an HTTP MCP server is aborted after max(the server's `timeout`, else MCP_TOOL_TIMEOUT, else 60000 ms; MCP_TIMEOUT, else 30000 ms). Its debug log for this hub shows `timeoutMs: 60000`. None of the arms' .mcp.json files sets `timeout`, the README template doesn't either, and drivers.CLAUDE_ENVIRONMENT sets no MCP_TOOL_TIMEOUT.
  Fix: Give each arm's .mcp.json, and the README template, a per-server timeout above the longest wait, e.g. {"type":"http","url":"${COORD_MCP_URL}","timeout":330000}. I checked that `claude mcp add-json` accepts and stores this key. Alternatively set MCP_TOOL_TIMEOUT=330000 in drivers.CLAUDE_ENVIRONMENT, or cap waits on the MCP path below 55 s. Also apply the hub-side fix in the next finding, so a caller that is gone never takes the answer.
- [mcp, minor] experiment/coordbench/mcp.py: The hub ignores notifications/cancelled: handle() returns None for every notification. A tools/call whose client has cancelled or disconnected keeps running, and a blocking tool then takes what it waited for and writes it to nobody. The 2025-06-18 cancellation rules say receivers SHOULD stop processing and not respond. Here it loses data and inflates the metrics.
  Fix: Track each session's in-flight tools/call ids. On notifications/cancelled, mark the id cancelled and wake run.lock, and have blocking tools check a `call.cancelled` flag in their wait predicate before taking anything. Also, when HubHandler.reply fails with a ConnectionError on a tools/call, let the arm undo what it took, e.g. put the message back at the head of the inbox or the response back on its queue, or have waits take the item only once the reply has been written.
- [mcp, minor] experiment/coordbench/hub.py: post_mcp never reads MCP-Protocol-Version. The 2025-06-18 transport says a server that receives an invalid or unsupported version MUST respond with 400 Bad Request. The 2026-07-28 HTTP binding, which Claude Code already probes with, expects a legacy server to answer that probe with a 4xx.
  Fix: In post_mcp, when the header is present, the body is not an initialize, and the version is not in mcp.PROTOCOL_VERSIONS, reply 400 with a JSON-RPC error that has no id. I verified this with a patched copy: Claude Code got 400 on its probe, fell back to initialize, and `claude mcp list` still showed Connected.
- [mcp, minor] experiment/coordbench/mcp.py: handle() does not validate message shapes. Bad params crash into -32603 instead of -32602. One bad batch member turns every member into -32603, including members that already ran. Null and boolean ids are answered as requests, although MCP ids MUST be a string or integer and never null. A non-string method gets -32601 instead of -32600. An empty batch gets 202 instead of one Invalid Request error. Parse errors and invalid messages get HTTP 200 with an `"id": null` error; neither MCP schema allows a null id (2025-11-25 omits it), and 2025-06-18 asks for an HTTP error status for input the server cannot accept. hub.opens_session also issues an Mcp-Session-Id for an initialize that was answered with an error.
  Fix: Validate before dispatch: id must be str or int and not bool, else -32600; method must be str, else -32600; params must be a dict or absent, else -32602; the tool name must be str, else -32602. Treat [] as a single -32600. In handle_body, catch exceptions per batch member so each member gets its own answer. In post_mcp, return 400 for a parse error or a lone invalid message, and issue a session only when the initialize answer is a result.
- [mcp, minor] experiment/coordbench/bridge.py: The bridge acts as a Streamable HTTP client but never re-initializes after a 404 to a request that carried Mcp-Session-Id, which 2025-06-18 says a client MUST do. It keeps sending the stale id, so the stdio client, which has no session of its own, fails every call from then on, whereas an HTTP client would recover.
  Fix: Keep the stdio client's last initialize params. On an HTTPError 404 to a request sent with a session id, clear session_id and protocol_version, post the saved initialize and notifications/initialized without writing their answers to stdout, then retry the original message once.
- [mcp, minor] experiment/coordbench/hub.py: Every client that drops a keep-alive connection makes socketserver print 'Exception occurred during processing of request ... ConnectionResetError' with a full traceback. The error comes from readline in handle_one_request, outside dispatch's try. Claude Code drops the connection each time it exits, and run.py sends hub stderr to hub.log, so every agent's exit leaves a traceback there that reads like a hub failure.
  Fix: Override HubServer.handle_error: if sys.exc_info()[1] is a ConnectionError, return quietly; otherwise call super().handle_error.
- [mcp, minor] experiment/coordbench/run.py: The transport's security warning says a local server SHOULD bind to localhost and SHOULD authenticate every connection. start_hub (line 284) binds 0.0.0.0, and /mcp and /rpc take no credential; COORD_ADMIN_TOKEN guards only /api. The only thing standing in for a credential is the URL: the run id is '<arm>-<task>-<features>-<6 hex>', so 24 random bits. The README covers agents impersonating each other, but not exposure to the rest of the network.
  Fix: Bind to the Docker bridge gateway, the address host.docker.internal resolves to, instead of 0.0.0.0. Or give each agent a bearer token that post_mcp and post_rpc check, carried by .mcp.json "headers": {"Authorization": "Bearer ${COORD_AGENT_TOKEN}"} and by cli.py.
- [fidelity, blocking] /home/user/sdlc-template/experiment/coordbench/kit.py: team arm: wait_for_message behaves differently from CooperBench's own team run. In CooperBench's run the tool never returns a message. coop_msg.py writes to `run:<id>:<agent>:inbox`, because it keeps the `#run:<id>` fragment of COOP_REDIS_URL as a prefix. team_harness/mcp_server.py strips that fragment and BLPOPs `<agent>:inbox`, with no prefix. So every call times out with the no-message marker, and the inbox is left for coop-recv. coordbench's kit.wait_for_message really hands over the oldest message and removes it from the inbox. kit.py's and arms/team/arm.py's docstrings call this tool 'the long poll CooperBench gives its CLI agents in team mode'. The tool text also differs: CooperBench's description says 'Prefer this to busy-polling coop-recv' and has a timeout_ms description, and CooperBench applies no upper clamp, where coordbench caps at 30000.
  Fix: Decide which way to go and write it down. For fidelity, the team arm's wait_for_message would block for timeout_ms, return the no-message marker and leave the inbox alone (CooperBench's real behaviour); its description would also be CooperBench's text. Alternatively, keep the working long poll as a deliberate, documented deviation in README and in the team arm's 'Where this differs' list, and stop calling it CooperBench's tool.
- [fidelity, blocking] /home/user/sdlc-template/experiment/coordbench/hub.py: Every agent's MCP initialize carries server instructions, which Claude Code puts into the system prompt. CooperBench's agents get none: solo and coop have no MCP server at all, and the team server sends no instructions. The text is `coordbench run <id> under the <arm> arm: you are <agent>, role <role>; these tools are how you coordinate with the other agents.` For solo this is false: the arm has zero tools and no other agents. It also names the arm and a role term ('peer') CooperBench never uses. Hub.instructions (line 233) is passed by answer_mcp for every arm, and the claude-cli driver loads the plugin, and so the MCP server, even for solo.
  Fix: Send no instructions by default: make Hub.instructions return "", or ask the arm for them through an Arm.instructions() that is empty for solo, coop, coop-git and team. For an arm with no tools, such as solo, leave out its .mcp.json, or have the driver skip loading the MCP server, so the baseline's context matches CooperBench's.
- [fidelity, minor] /home/user/sdlc-template/experiment/coordbench/arms/coop/skills/coordbench-coop/SKILL.md: The coop and coop-git skills add a sentence the authors' prompt lacks: 'Messages are never pushed into your conversation; you see them only when you receive them.' coop/arm.py says the skill 'restates the prompt and adds nothing'. The solo skill adds text about the MCP server `coordbench` listing no tools. Each of these arms also lists one extra skill in the system prompt, which CooperBench's agents do not have.
  Fix: Drop the added sentences so the skills are pure restatements, or ship the CooperBench arms without skills, as for team.
- [fidelity, minor] /home/user/sdlc-template/experiment/coordbench/kit.py: The messaging commands do not keep coop_msg.py's arguments, exit codes or output, though README says the commands keep them ('the same arguments and exit codes'). Affects coop, coop-git and team. The differences:

- [fidelity, minor] /home/user/sdlc-template/experiment/coordbench/arms/team/arm.py: The team arm's own deliberate deviations change what the agent sees. Requests to unknown agents are refused. Multi-word titles are joined. An empty title is refused. --wait is capped at 300 s (LONGEST_WAIT_SECONDS). The docstring lists these, but the brief allows only the MCP tool names as a difference.
  Fix: Port CooperBench's behaviour:

- refuse extra words with exit 2, as argparse does

- [runner, blocking] experiment/report.py: pair_outcome reads only result["agents"]. CooperBench's solo runner (runner/solo.py) writes a singular "agent" block. So for CooperBench's own solo baseline the report counts 0 tokens and never sees an agent in Error. CooperBench still evaluates pairs whose agent errored (core.py marks them "done" and submits _evaluate_single), so those pairs have an eval.json and are scored as failures. coordbench's solo result.json uses "agents" (run.py result_record), so its errored pairs are left out of the rate instead. The two solo rows are therefore measured differently.
  Fix: In pair_outcome, use `agents = result.get("agents") or ({"solo": result["agent"]} if isinstance(result.get("agent"), dict) else {})`. Add a test with CooperBench's solo shape.
- [runner, minor] experiment/coordbench/run.py: settings_from never resolves log_dir or cooperbench_dir (--log-dir, --cooperbench-dir and $COOPERBENCH_DIR are taken as given). With the session driver, a relative workspace path in `-v <workspace>:/workspace/repo` is read by docker as a volume name, so provisioning fails. Scoring also breaks: cooperbench_test checks .venv/bin/python relative to the runner's directory but starts it with cwd=cooperbench_dir, and passes src and dataset_dir as relative paths. So a relative CooperBench directory fails only after the agents have run.
  Fix: In settings_from, call `.resolve()` on log_dir and cooperbench_dir (and on cooperbench_home()). Alternatively, resolve both inside new_plan and cooperbench_test.
- [runner, minor] experiment/coordbench/drivers.py: stop_claude uses `pkill -f 'claude --verbose'`. pkill is missing from every Debian-slim task image: none of the 30 dataset Dockerfiles installs procps, and python:3.11-slim has no pkill. After the docker exec client is killed at the timeout, Claude Code keeps running in the container. Unless --keep is set, teardown removes the container a little later. With --keep it runs on indefinitely, spending the subscription and still able to push to the shared remote.
  Fix: Bound the agent inside the container: run claude under coreutils `timeout -k 30 <timeout_s>` in claude_script. Alternatively, write the shell's pid (`echo $$ > /tmp/coord-claude.pid; exec claude ...`) and stop it with the builtin `kill $(cat /tmp/coord-claude.pid)`.
- [runner, minor] experiment/coordbench/run.py: The README says arm.json plugin URLs are each loaded with --plugin-dir or --plugin-url. resolve_plugin, however, sends every URL to fetch_plugin, which runs `git clone --depth 1`. A plugin .zip URL, which is the only form --plugin-url takes, can never load.
  Fix: Pass .zip URLs through as `--plugin-url` in claude_flags, or download and unzip them on the host. Otherwise, change the README to say URLs must be git repositories.
- [runner, minor] experiment/coordbench/drivers.py: Cost is dropped. summarize_stream discards the result event's total_cost_usd, and AgentOutcome has no cost field. As a result, result.json lacks the fields CooperBench's coop.py and solo.py write: per-agent cost and patch_lines, plus total_cost and total_steps. CooperBench's utils.get_run_totals and its run summary read total_cost, so a coordbench run shows $0 next to the authors' runs.
  Fix: Add cost=float(event.get('total_cost_usd') or 0) to AgentOutcome via summarize_stream (as parse_stream_json does). Have agent_record and result_record write cost, patch_lines, total_cost and total_steps.
- [runner, minor] experiment/coordbench/drivers.py: SessionDriver.wait returns AgentOutcome(status="Submitted") with every token count and steps at 0. report.py sums these into "Tokens per pair", so a session-driver run reports 0 tokens as if that had been measured.
  Fix: Record unknown usage as null in agent_record for drivers that cannot measure it (for example a driver attribute measures_usage=False). Have report.py show '-' when every agent's usage is null, or let finish take the subagents' reported usage.
- [runner, minor] experiment/coordbench/drivers.py: container_arm_dir keeps only the basename of the arm directory. A non-built-in arm with a built-in arm's name is therefore copied by docker cp over /opt/coordbench/arms/<name>, which install_coordbench has just filled with the built-in arm. The two directories merge, and Claude loads a mix of both: for example, two skills when the copy renamed its skill directory.
  Fix: Copy non-built-in arms under their own root, for example /opt/coordbench-arms/<safe_name(resolved path)>, and have container_arm_dir return that path for arms that are not built in.
- [robust, blocking] /home/user/sdlc-template/experiment/coordbench/arms/team/arm.py: The task-list mirror (mirror_task_list, lines 408-431) runs in the hub on the host and follows a symlink an agent plants in the shared volume. It writes task files into whatever directory `tasks` points at, and it unlinks every *.json there that is not a live task id. The hub has to run as root to write a Docker volume's host path, so an agent inside its container can make the hub delete files in any host directory. The README draws exactly this trust line: the hub refuses arm directories because an agent could write one into a shared volume.
  Fix: Treat the volume as untrusted. Open the tasks directory with os.open(..., O_RDONLY|O_DIRECTORY|O_NOFOLLOW) under the resolved shared root, then do every write, rename, scandir and unlink relative to that dir_fd (os.replace with src_dir_fd/dst_dir_fd, os.unlink with dir_fd). Skip the mirror if `tasks` is a symlink or is not a directory. A plain realpath check before writing would leave a race window.
- [robust, minor] /home/user/sdlc-template/experiment/coordbench/kit.py: wait_for_message (lines 68-77) checks the inbox in one hold of run.lock (wait_until) and pops it in a second hold. Between the two, another call by the same agent can drain the inbox: a receive_messages, or a second wait_for_message woken by the same notify_all. pop(0) on the empty list then raises IndexError, and the agent gets 'the wait_for_message tool failed inside the hub'. The bridge runs a client's requests on parallel threads by design, so concurrent calls from one agent are expected. Two smaller problems in the same function: the wait never looks at run.closed, so close wakes it only to sleep again until the timeout (up to 30 s), and timeout_ms values such as '5000.0' or Infinity crash with ValueError or OverflowError instead of being refused.
  Fix: Wait and pop under one hold, e.g. `with run.lock: if not run.lock.wait_for(lambda: bool(inbox(run, me)) or run.closed, t): return marker; if not inbox(run, me): return marker; message = inbox(run, me).pop(0)`. The RLock-backed Condition releases fully while it waits, so nesting is safe. Parse timeout_ms with a try that refuses non-numbers and non-finite values as a ToolError.
- [robust, minor] /home/user/sdlc-template/experiment/coordbench/mcp.py: handle() assumes params is an object and the tool name is hashable. A request with params as a list raises AttributeError in initialize_result or call_tool, and {"name": [..]} raises TypeError at `name not in tools`. handle_body processes a batch in one comprehension with no per-message guard, so one malformed request throws away the answers to every request in the batch. hub.answer_mcp then answers every id with -32603, including tools/calls that already ran and changed state, so a client that retries repeats them. /rpc with a list as "tool" gets a 500 for the same reason.
  Fix: In handle, return INVALID_PARAMS when params is present but not a dict. In call_tool, check isinstance(name, str) before the lookup. In handle_body, catch exceptions per message so each request gets its own answer (-32603 only for the message that failed).
- [robust, minor] /home/user/sdlc-template/experiment/coordbench/kit.py: deliver (lines 29-35) appends the message to the inbox before run.emit computes chars=len(content). Non-string text (an integer, from an MCP client that ignores the schema) is therefore delivered and then reported to the sender as a hub crash. broadcast stops after the first peer, so delivery is partial. A list as `to` crashes with TypeError (unhashable) where a refusal belongs.
  Fix: Validate before mutating: refuse a non-string `to` or `text` with a ToolError (or coerce with str()), and compute chars before the append. In broadcast, check every recipient first so it delivers to all or to none.
- [robust, minor] /home/user/sdlc-template/experiment/coordbench/arms/team/arm.py: The hub keeps answering tools after close, and mirror_if_shared ignores run.closed. A late coop-task-list therefore recreates shared_dir_host/tasks with mkdir(parents=True) after the runner's teardown has removed the volume. Over many runs this leaves stray root-owned directories under Docker's volume root. The sdlc arm, by contrast, closes its gate and refuses late calls.
  Fix: Skip the mirror once run.closed is set (read it in the same lock hold as the snapshot), and create only the `tasks` leaf: mkdir(exist_ok=True) without parents=True, so a removed volume root stays removed.
- [robust, minor] /home/user/sdlc-template/experiment/coordbench/arm.py: Run.emit (lines 154-164) appends to events.jsonl while it holds run.lock and lets an OSError escape. The escape happens after events.append and before notify_all. mcp.call_tool emits 'tool' outside its try. So once the log cannot be written (disk full, or the log directory cleaned away), every tool call of the run fails as a hub internal error, no message is delivered, and waiters are not woken. The file is meant to be a side record; the runner reads events from memory through /api/runs/{run}/events.
  Fix: Make the append best effort: catch OSError, complain once per run, keep the in-memory event, and call notify_all in a finally. Optionally move the write off run.lock with a small per-run file lock or a queue.
- [robust, minor] /home/user/sdlc-template/experiment/coordbench/hub.py: The hub never forgets a run. close_run marks it closed, but Hub.runs keeps the Run, its events, its prompts, its MCP session ids and its arm instance. resolve_arm re-executes arm.py into a fresh module for every run, and coop-git and team also load coop's and coop-git's modules. A batch hub, or a long-lived --hub serving many runners, grows without bound. An sdlc run that is never closed (the runner was SIGKILLed) also keeps its scratch clone until the hub exits.
  Fix: Let the runner release a run after it has fetched metrics and events (DELETE /api/runs/{run}, or drop closed runs after a grace period or beyond a bounded count of closed runs), and cache loaded arm classes per resolved directory instead of re-executing arm.py for every run.
- [robust, minor] /home/user/sdlc-template/experiment/coordbench/arms/sdlc/arm.py: issue_number (lines 411-418) checks the issue with str.isdigit, which accepts characters int() rejects: superscripts such as '2', and strings longer than the 4300-digit int limit. Those inputs crash with ValueError, and the agent gets 'claim_issue failed inside the hub' where a refusal belongs. Arabic-Indic digits are silently read as numbers.
  Fix: Accept only ASCII digits of sane length, e.g. re.fullmatch(r"#?\s*([0-9]{1,9})", text), and raise the existing ToolError otherwise.
- [robust, minor] /home/user/sdlc-template/experiment/coordbench/hub.py: parse_features (lines 281-287) accepts duplicate feature numbers and any number of features. With duplicates, the sdlc arm's setup maps the issue to the last agent only, so the other agent is told 'Your issue is #<issue>' and every claim it makes is refused. With many features, the coop and team prompts list every partner in every prompt, so the size of a run grows with the square of the feature count, and the hub keeps it forever (see the eviction finding).
  Fix: Refuse duplicate features with a 400, and cap the count (a task pair is 2; something like 16 leaves room) before the arm lays anything out.
